# ORA PoC 가상 실행기 및 에뮬레이터 아키텍처 설계 계획

본 문서는 ORA(Open Reconfigurable Architecture) 표준의 PoC(Proof-of-Concept)를
구현하기 위한 가상 실행기(Virtual Fabric Executor)와 하드웨어 에뮬레이션
환경의 설계 계획을 기술한다. 본 계획은 `docs/ora_poc_standard_specification.typ`
(계층별 인터페이스 규격)와 `poc/ora_bitstream/`(중립 바이트코드 v1.0 참조 구현,
테스트 46건 통과)의 직계 후속 산출물이다.

## 1. PoC 목표 및 검증 가설

PoC가 증명해야 하는 핵심 가설은 다음 세 가지이다.

| # | 검증 가설 | 성공 기준 (측정 가능) |
|---|----------|----------------------|
| H1 | ORA 중립 비트스트림이 물리 구현과 독립적으로 직렬화/복원된다 | v1.0 바이너리의 무결 인코딩·디코딩 (CRC 2중 검증), 임의 크기 넷리스트 왕복 손실 0 |
| H2 | 무테이블 소스 라우팅 + 단조 VC 계층화가 불규칙 토폴로지에서 무데드락이다 | *1차:* 컴파일된 라우트 전체의 CDG(채널 의존성 그래프) 정적 비순환 검사. *보조:* 결함 주입·재컴파일 후 100만 패킷 시뮬레이션에서 데드락 0건, VC1→VC0 전이 0건 |
| H3 | Valid/Ready 탄성 파이프라인이 슬랙 탄력성을 제공한다 | 임의 경로에 FIFO 버퍼 0→N개 삽입 시 토큰 시퀀스(기능적 결과) 동일. 스루풋은 사이클을 이루는 데이터플로우 경로에서는 감소할 수 있으므로 기준에서 제외 |

비목표(Non-Goals): 성능 최적화, 실리콘 타이밍 클로저, CIRCT 프론트엔드 전체
통합. 이들은 PoC 이후 단계로 연기한다.

## 2. 전체 아키텍처 (모듈 분해)

```
┌────────────────────────────────────────────────────────────┐
│  ora-bitstream   (완료)                                     │
│  v1.0 바이너리 인코더/디코더 + 플릿 패킹 유틸리티            │
└──────────────┬─────────────────────────────────────────────┘
               │ OraBitstream 객체 (디코딩된 IR)
┌──────────────▼─────────────────────────────────────────────┐
│  M1  fabric-graph   패브릭 그래프 구축기                     │
│  · VRB/엣지/라우트 레코드 → 실행용 그래프로 인스턴스화        │
│  · 타일/NI/라우터 포트 위상 구성 (2D 격자 + 결함 주입)       │
└──────────────┬─────────────────────────────────────────────┘
┌──────────────▼─────────────────────────────────────────────┐
│  M2  elastic-core   이벤트 구동 탄성 실행 엔진                │
│  · Valid/Ready 채널, Join/Fork/Merge 프리미티브             │
│  · 토큰 점화(Fire) 의미론, 백프레셔 전파                    │
│  · 슬랙 실험용 파라미터화 FIFO 삽입                          │
└──────────────┬─────────────────────────────────────────────┘
┌──────────────▼─────────────────────────────────────────────┐
│  M3  noc-router    ORA-N 라우터/NI 시뮬레이터               │
│  · 3비트 포트 디코드, 논리 시프트 >>>3, 홉 감소             │
│  · 체인드 헤더 처리, VC 승격 카운트다운 (§2.2 규약 정합)      │
│  · VC0/VC1 물리 버퍼 분리, CDG 덤프 훅                      │
└──────────────┬─────────────────────────────────────────────┘
┌──────────────▼─────────────────────────────────────────────┐
│  M4  verifier      가설 검증 하네스                          │
│  · H1: 랜덤 비트스트림 퍼지 왕복 (property-based)           │
│  · H2: CDG 정적 비순환 검사(1차) + 데드락 감시기(보조)      │
│  · H3: FIFO 삽입 전후 골든 결과 비교 (비트 정합)            │
└────────────────────────────────────────────────────────────┘
```

## 3. 모듈별 상세 설계

### M1 fabric-graph — 패브릭 그래프 구축기

- 입력: `OraBitstream` 디코딩 결과 (M0 산출물).
- 출력: `FabricGraph` — 노드(`VrbNode`, `RouterNode`, `NINode`)와
  `ElasticChannel` 엣지로 구성된 실행 가능 그래프.
- 규칙:
  - VRB 레코드 순서가 곧 `vrb_id`이며, 넷리스트 엣지의 `src/dst_port`는
    `port_bindings`와 정합해야 한다 (정합 실패 시 `FabricError`).
  - 결함 주입: 링크 비활성화 목록을 받아 그래프에서 엣지를 제거한 뒤
    *연결성을 점검*하고 Up\*/Down\* 신장 트리와 소스 라우팅 헤더를
    재컴파일한다. 토폴로지 비종속성은 "어떤 토폴로지든 컴파일러가
    처리한다"는 뜻이지, 낡은 라우트가 결함을 버틴다는 뜻이 아니다.

### M2 elastic-core — 탄성 실행 엔진

- 이벤트 구동(event-driven) 방식. 글로벌 클록을 모델링하지 않고
  채널 점화(Fire) 조건(`VALID & READY`)을 이벤트로 처리한다.
- 채널 상태 머신: `Idle → Valid → Fire` / `Valid → Stall(백프레셔)`.
- Join/Fork/Merge 의미론은 규격서 §1.2의 불리언식을 그대로 코드화하며,
  규격과의 정합을 위해 각 프리미티브의 진리표를 테이블 기반으로 유지한다.
- 슬랙 실험 인터페이스: 임의 채널에 지연 FIFO(depth k)를 동적 삽입할 수
  있는 `insert_slack(channel_id, k)` API를 제공한다 (H3 검증용).

### M3 noc-router — ORA-N 라우터 시뮬레이터

- 라우터 상태는 오직 (VC0 버퍼, VC1 버퍼, 크로스바)만 보유 —
  **라우팅 테이블이 없음**을 코드 수준에서 강제한다 (테스트로 검증).
- 헤더 처리는 규격서 §2.2 의사코드를 그대로 코드화한다:
  1. `Bit[2:0]` 디코드 → 출력 포트
  2. VC 승격 카운트다운: `vc_transition_hop` 값이 `000`이면 이번 홉에서
     VC1으로 단조 승격 후 센티널 `111` 기록, `001`–`110`이면 1 감산,
     `111`이면 불변
  3. `chained == 1`이면 소진 헤더 폐기 후 다음 플릿(유형 `00`)을 헤더로 해석
  4. 방향 벡터 `>>>3` 논리 시프트 (부호 확장 없음 — 규격 정합)
- CDG 덤프 훅: 노드는 (방향 링크, VC) 채널 쌍, 간선은 컴파일된 라우트의
  연속 홉 쌍. `verify: cdg_is_acyclic()` 정적 검사가 H2의 1차 증명이다.

### M4 verifier — 가설 검증 하네스

| 검증 | 방법 | 통과 조건 |
|------|------|-----------|
| H1 | hypothesis 기반 퍼지: 임의 VRB/엣지/라우트 생성 → 인코딩 → 디코딩 → 동치 비교 | 10,000 샘플 왕복 동치 100% |
| H2 | 1) 결함 주입→연결성 점검→트리/라우트 재컴파일. 2) CDG 정적 비순환 검사(1차 증명). 3) 핫스팟 트래픽 포함 100만 패킷 시뮬레이션(보조 확인) | CDG 순환 0건(정적), 시뮬레이션 데드락 0건, VC1→VC0 전이 관측 0건 |
| H3 | 골든 넷리스트 실행 → 경로별 FIFO 0..8 삽입 → 토큰 시퀀스 비교 | 토큰 시퀀스(기능적 결과) 동등 100% (스루풋은 기준에서 제외) |

## 4. 구현 스택 및 디렉터리 계획

- 언어: Python (uv 관리, 루트 워크스페이스와 동일한 3.14 사용). 이벤트 큐
  단순성 우선; 성능 병목 발생 시 M2/M3만 Rust로 재작성하는 이중 경로를 예비로 둔다.
- 테스트: pytest + hypothesis (H1), 커스텀 데드락 감시기 (H2).
- 디렉터리:

```
poc/ora_bitstream/     # 완료: v1.0 코덱 (46 tests green)
poc/ora_fabric/
  src/ora_fabric/
    graph.py           # M1 fabric-graph
    elastic.py         # M2 elastic-core
    router.py          # M3 noc-router
    verify.py          # M4 verifier (harness entry)
  tests/
    test_graph.py
    test_elastic.py    # H3 슬랙 탄력성
    test_router.py      # H2 무데드락 + 체인드 헤더 + VC 승격
    test_roundtrip.py   # H1 퍼지 왕복
  examples/
    demo_mesh4x4.py     # 결함 주입 데모 시나리오
```

## 5. 마일스톤

| 단계 | 산출물 | 완료 판정 |
|------|--------|-----------|
| S1 | M1 + M2 (그래프 + 탄성 코어) | Join/Fork/Merge 진리표 테스트 통과, 슬랙 삽입 API 동작 |
| S2 | M3 (라우터) | 체인드 헤더·VC 승격·논리 시프트 단위 테스트 통과 |
| S3 | M4 (하네스) | H1/H2/H3 전 항목 통과, `demo_mesh4x4.py` 데드락 0 확인 |
| S4 | SpinalHDL 레퍼런스 RTL (`poc/ora_rtl/`) 과 co-sim. Podman 이미지 `localhost/ora-rtl` 내 Verilator 5.020 | 시뮬레이터·RTL 플릿 트레이스 정합 |

S1~S3를 Python으로 완결하는 것이 1차 목표이고, S4는 표준 사양서
로드맵 2단계(SkyWater 130nm MPW)로 연결되는 관문(Gate)이다.

### S4 진행 현황

실행: `just --justfile poc/ora_rtl/cosim.just cosim-all` (sbt, Verilator, 시뮬레이션 모두 컨테이너 내부).

| 범위 | RTL | 골든 모델 | 결과 |
|------|-----|-----------|------|
| 단일 채널 코어 | `OraRouterCore` (입력 1, 출력 1 + eject, 백프레셔) | `NoCRouter` 단일 경로 | 8/8 시나리오 트레이스 일치 |
| 다중 포트 라우터 × 2 체인 | `OraRouter` (7포트 × 2VC FIFO, (포트, VC) 락, 포트별 RR, 깊이 2) | `NoCRouter` 2개 (R0.EAST ↔ R1.WEST) | 9/9 시나리오 트레이스 일치 |

중재 규칙은 사양서 "웜홀 자원 관리 및 사이클 중재 계약" 절을 따른다. co-sim 시나리오가 실제로 결함을 잡는지 변이(mutation) 검사로 확인했다. RR 우선순위 반전, 하류 크레딧 무시, 헤더 락 검사 제거 세 변이 모두 1개 이상의 시나리오에서 불일치를 냈다.

남은 한계:

- co-sim 토폴로지는 2-라우터 선형 체인뿐이다. 메시(예: 4×4) 규모의 RTL co-sim과 무작위 트래픽 co-sim은 아직 수행하지 않았다.
- 로컬 배출은 항상 수신 가능(ready)하다고 가정한다. NI 측 배출 백프레셔는 모델링하지 않았다.
- 합성, 타이밍, 면적은 평가하지 않았다(비목표).
